# Tomos テーマ基盤拡張 開発プラン v1

対象: Tomos v0.1.0-beta.1 以降  
策定日: 2026-08-18

本計画は、Tomosのテーマ環境を普遍的に拡張し、標準テーマの改修性、独自テーマ制作、サイト固有設定、トップページ向け構造化データ提供、将来のテーマ配布サイトへ接続できる基盤を整備するための開発計画である。

研究室向けテーマは実際のセールスを想定した主要ユースケース、Tomos公式サイトは先行運用テスト先と位置づける。Tomos本体には研究室固有の業種概念を持ち込まない。

## 0. 開発開始時の宣言ルール

この開発では、実装・調査・修正を開始するたびに、最初に現在位置を宣言する。宣言なしにコード変更へ入らない。

```text
【現在位置】Phase X / Gate Y
【今回の目的】今回達成する1つの目的
【変更対象】触るファイル・責務・API
【非対象】今回触らない範囲
【完了条件】この作業を終えたと判断する条件
```

例:

```text
【現在位置】Phase 2 / Gate 2直前
【今回の目的】サイト固有テーマ設定を安全に読み込む
【変更対象】ThemeSettings、TemplateRendererのcontext追加、テスト
【非対象】News API、テーマ配布サイト、GUI設定画面
【完了条件】既存テーマ無変更で回帰成功、設定なし環境で後方互換を維持
```

## 1. 現在地点

Tomosはv0.1.0-beta.1へ移行済みで、alpha期の主要機能を一般利用を想定した安定運用段階へ移している。投稿、設定、索引、HTML cache、Update、Passkey等についてrollback・世代整合・同時更新・failure injectionが強化されている。

1ファイルインストーラー、署名付きUpdate、公式オンライン更新経路も成立している。

テーマ基盤では、トップページ専用`templates/home.html`、配列反復を含むテンプレート構文、テーマZIP追加、ThemeValidator等がすでに存在する。

一方、以下は未整備である。

- サイト固有テーマ設定
- 汎用的なトップページ用構造化データAPI
- テーマ互換性宣言
- テーマ配布サイトを見据えたmetadata
- テーマ制作者向けの正式なAPI仕様書

## 2. 開発目的

- Tomos本体のテーマ機構を、単なる見た目の切り替えから、実用的なサイト制作基盤へ拡張する。
- 一般利用者はテーマを簡単に追加・選択できる状態を維持する。
- 独自テーマ制作はHTML/CSSとTomosテーマ仕様を理解する技術者向けでよい。
- 標準テーマも、詳しい制作者が改変・派生しやすい構造にする。
- サイト固有の低頻度設定と、日常的なMarkdown更新を明確に分離する。
- Tomos公式サイトで先行運用し、Newsの二重更新を解消して実運用テストする。
- 研究室向けテーマを、実際のセールスを想定した最初の商用ユースケースとして制作する。
- 将来のTomos Theme Directoryを成立させられる互換性・配布仕様を準備する。

## 3. 設計原則

### Tomos本体

公開判定、索引、構造化データ、URL生成、安全性、テーマAPIを担当する。

### テーマ

HTML構造、CSS、表示表現を担当する。テーマ内PHP禁止を維持する。

### サイト固有設定

Hero、ロゴ、キーカラー、News表示条件など、変更頻度の低い初期設定を一箇所に集約する。

### Markdown

News、Research、Members、Publications等の日常的に更新するコンテンツの正本とする。

### 一般利用者とテーマ制作者

テーマを使うことは簡単にするが、テーマを作ることまではノーコード化しない。

## 5. Phase 0 — 仕様固定・現行テーマ基盤監査

### 目的

既存beta.1のテーマ機構を正確に把握し、今回の改修境界を固定する。

### 主な作業

- TemplateRenderer、ThemeValidator、ThemePackagePolicy、Theme追加・切替・Update保護範囲を再監査する。
- `home.html`、配列section、URL変数、raw HTML allowlistの現仕様を確定する。
- 標準テーマ6種の構成差、共通変数、独自依存を一覧化する。
- Update時に利用者追加テーマとサイト固有資産を保護する境界を確認する。
- 今回導入するAPI名・設定ファイル名・資産配置をADRまたは仕様書で固定する。

### 成果物

- 現行テーマ仕様監査メモ
- テーマAPI v1仕様
- 非対象一覧
- 後方互換条件

### Gate 0

- 現行6標準テーマが無変更で動作する前提を確認できている。
- 既存Update・Theme追加・Theme切替の責務と衝突しない。
- 研究室固有の業種概念をTomos本体へ入れていない。
- 未確定のAPI名を残したままPhase 1へ進まない。

## 6. Phase 1 — テーマ契約・互換性基盤

### 目的

独自テーマを安全に配布・改変・将来公開できる契約を整える。

### 主な作業

- `theme.json`のmetadata拡張候補を整理する。
- `requires_tomos`等の互換性宣言方式を実装するか、このPhaseで最終判断する。
- `supports`の意味を整理し、実装機能と表示用metadataを混同しない。
- 標準テーマの派生方法（name変更、共存、Update保護）を明文化する。
- テーマZIP検証で新metadataを安全に扱う。

### 成果物

- `theme.json`仕様 vNext
- テーマ互換性判定
- 独自テーマ派生ガイドの骨格

### Gate 1

- 古いTomosへ新API必須テーマを誤導入する事故を防げる、または明確に検知できる。
- 既存テーマZIPが互換性を失わない。
- 標準テーマのUpdateと利用者派生テーマが混線しない。
- Gate 1通過時点でテーマ配布物の契約が固定される。

## 7. Phase 2 — サイト固有テーマ設定

### 目的

テーマ本体とサイト固有の初期設定・画像を分離し、設定を散在させない。

### 主な作業

- `theme-settings.php`等の単一設定ファイル方式を実装する。
- Hero、ロゴ、キーカラー、News設定等を許可キー方式で読み込む。
- サイト固有アセットをテーマZIP外の保護領域へ配置する。
- 設定なし・一部欠落・不正値でも既存サイトを壊さないフォールバックを実装する。
- TemplateRendererへ`theme.*` contextを追加する。

### 成果物

- ThemeSettings責務
- サイト固有asset URL生成
- `theme.*` API
- 自動テスト

### Gate 2

- `theme-settings.php`が存在しない既存環境で完全後方互換。
- Updateでサイト固有設定・画像が上書きされない。
- パストラバーサル、危険URL、想定外キーを無害化。
- 設定解析ロジックがApp.phpへ散在していない。
- Gate 2通過後に初めてNews APIへ進む。

## 8. Phase 3 — 構造化News API

### 目的

指定されたNewsソースから公開済みページを抽出し、HTMLではなく構造化配列としてテーマへ提供する。

### 主な作業

- Newsソースパス、enabled、limit等をサイト固有設定から取得する。
- 既存の公開判定・MetadataIndex・並び順を再利用する。
- `home.news_items`、`home.has_news`、`home.news_url`を追加する。
- 各itemは`date`、`date_display`、`title`、`url`を最低限提供する。
- Tomos本体ではNews HTMLを生成しない。
- 0件、OFF、長いタイトル、同日複数投稿、下書き、取り下げを検証する。

### 成果物

- NewsProvider責務
- `home.*` API
- テンプレート反復サンプル
- 性能・回帰テスト

### Gate 3

- トップ表示と`/news/`一覧が同じMarkdown正本・公開判定に従う。
- News表示のために本文全件再解析を行わない。
- 既存の公開順序規則と不整合を作らない。
- News APIが研究室専用の命名・ロジックになっていない。
- 既存テーマには影響しない。

## 9. Phase 4 — Tomos公式サイト先行適用

### 目的

新テーマ基盤をTomos自身の公式サイトへ適用し、実運用で検証する。

### 主な作業

- 公式サイトの手動News二重更新箇所を洗い出す。
- 公式サイトテーマを新News APIへ移行する。
- トップページNewsとNews一覧ページを`/news/`の単一正本へ統合する。
- 実際のニュース投稿、修正、取り下げ、同日投稿で運用確認する。
- テーマ設定変更はFTP/SFTP運用で検証する。

### 成果物

- 公式サイト対応テーマ
- 運用チェックリスト
- 実運用で見つかったAPI改善点

### Gate 4

- News投稿1回でトップと一覧が自動整合する。
- 従来発生していた二重更新ミスの原因が解消されている。
- 通常投稿・RSS・Sitemap・検索等へ悪影響がない。
- 最低1サイクル以上の実運用で重大な設計不足がない。
- API変更が必要ならPhase 2またはPhase 3へ戻し、仕様を修正して再通過する。

## 10. Phase 5 — 標準テーマ整備・開発者ドキュメント

### 目的

標準テーマを、一般利用者向け完成品であると同時に、技術者向けの良質なサンプル実装にする。

### 主な作業

- 標準テーマの構造・命名・コメント・変数利用を整理する。
- 少なくとも1テーマで新テーマAPIの模範実装を示す。
- コピー→name変更→独自テーマ化の手順を文書化する。
- テーマAPI一覧、必須ファイル、禁止事項、ZIP仕様、互換性ルールをまとめる。
- ブラウザCSS編集やノーコードテーマビルダーは実装しない。

### 成果物

- Theme Developer Guide
- テーマAPIリファレンス
- 最小テーマサンプル
- 派生テーマ作成手順

### Gate 5

- HTML/CSSを扱える制作者が本体PHPを読まずにテーマを作れる。
- 標準テーマが特殊実装に依存せず参考実装として読める。
- テーマ開発を一般ユーザー向けGUIへ広げていない。
- 既存テーマ横断回帰が成功する。

## 11. Phase 6 — 研究室向けテーマ制作・商用検証

### 目的

新テーマ基盤を使い、実際のセールス・制作・納品・公開後保守までを想定した高品質な研究室向け商用テーマを制作する。

研究室テーマはデモ専用ではなく、Theme ZIPを制作中に繰り返し調整・再投入し、公開後も同じtheme IDを更新できる商用品として扱う。詳細な実案件モデルは`docs/theme/lab-commercial-model-v1.md`を基準とする。

### 主な作業

- 制作スタッフへTheme Developer GuideとAPI仕様を渡す。
- Hero、News、`index.md`本文を中心にトップページを設計する。
- Members、Research、Publications等は通常Markdownページとして扱う。
- 研究室ごとのHero画像・コピー・ロゴ等はサイト固有設定で管理する。
- 初期サイト固有設定には必要に応じFTP/SFTPを利用する。
- 制作中はTomos Postから同一theme IDのTheme ZIPを繰り返し投入し、HTML/CSS/assetsの調整を反映する。
- 同version再投入、上位version更新、active theme更新、全体置換、rollbackを実案件フローで検証する。
- Theme ZIP再投入で`theme-settings.php`、`theme-assets/`、`content/`、`config.php`が保持されることを確認する。
- 研究室側の日常更新ではテーマ設定を触らず、Tomos PostとMarkdown中心で運用できることを確認する。
- 日本語・英語ページを混在させ、`page.language`を使った表示を検証する。

### 成果物

- 研究室向け商用テーマ v1
- デモサイト
- `docs/theme/lab-commercial-model-v1.md`
- 営業・制作・納品・更新時の導入手順
- Theme ZIP反復deploymentの実案件検証結果
- 制作工数・保守範囲の実測

### Gate 6

- 研究室固有機能をTomos本体へ追加せず実現できている。
- テーマだけで商用品として十分なデザイン差別化が可能。
- Hero、ロゴ、キーカラー等のサイト固有値がTheme ZIPから分離されている。
- Research、Members、Publicationsをv1では通常Markdownで運用できる。
- News投稿1回でトップと一覧が同じMarkdown正本へ従う。
- 制作スタッフが同じtheme IDのZIPを制作中に繰り返し投入できる。
- 同version再投入と上位version更新が成立し、削除済みthemeファイルが残留しない。
- active themeを更新してもtheme選択が維持される。
- Theme ZIP更新で`theme-settings.php`、`theme-assets/`、`content/`、`config.php`が保持される。
- 不正・非互換・配置失敗時に既存themeを破壊せずrollback/recoveryできる。
- 一般研究室ユーザーの日常運用はTomos PostとMarkdown中心のまま。
- 一般利用者も公開後の同一theme ID更新をブラウザから実行できる。
- PC、tablet、mobileで商用品として妥当な表示品質を満たす。
- 日本語・英語ページが研究室専用言語ロジックなしに`page.language`で表示できる。
- 制作者がTomos本体PHPを変更せず商用themeを制作できる。
- themeがMarkdown解析、公開判定、draft判定、URL生成を重複実装していない。
- 別の制作スタッフが営業・制作・納品・更新手順を再現できる。
- Theme / ThemeSettings / Markdown / Coreの責務を研究室固有例外なしで説明できる。
- 商用案件投入前に利用するCore APIは公式サイトまたは既存回帰で検証済みである。

## 12. Phase 7 — テーマ配布基盤の準備

### 目的

将来のテーマ配布サイトを可能にする情報設計と配布契約を固める。このPhaseでは配布サイト本体の開発を必須としない。

### 主な作業

- テーマ一覧に必要なmetadataを確定する。
- author、license、version、requires_tomos、supports、preview等を整理する。
- テーマ署名・信頼モデル・審査方針の必要性を検討する。
- Tomos Postからテーマ配布サイトへ接続する将来APIの境界を定義する。
- MIT標準テーマと商用・第三者テーマの扱いを分離できる設計にする。

### 成果物

- Theme Directory metadata仕様
- 将来API境界
- 配布・審査ポリシー草案

### Gate 7

- Tomos本体が特定の配布サイトに密結合していない。
- 第三者テーマを無条件に信頼する設計になっていない。
- テーマ作者・ライセンス・互換性をユーザーへ提示できる。
- このPhaseは独立プロジェクト化できる状態で終了可能。

## 13. Gate共通チェック項目

各Gateでは最低限、以下を確認する。

- PHP lintが成功する。
- 既存自動テストと新規回帰テストが成功する。
- `git diff --check`が成功する。
- 既存6標準テーマの表示・切替・テーマ追加が壊れていない。
- Tomos Updateで`config.php`、`content/`、利用者追加テーマ、サイト固有資産を意図せず変更しない。
- Markdown正本、DB不使用、テーマPHP禁止というTomosの基本原則を維持する。
- 新機能がApp.phpやTemplateRendererへ過度に集中せず、責務が分離されている。
- 通常ページ表示や投稿時に不要な全件再解析を増やしていない。
- 一般利用者向けUIへ不要な複雑さを持ち込んでいない。
- 仕様変更があった場合、コードだけでなくテーマAPI仕様・本開発プランも更新する。

## 14. 戻りGateのルール

Gateは一方向の承認ではない。

後続Phaseで前提不整合が判明した場合は、原因となるPhaseへ戻る。その際、局所パッチで辻褄を合わせず、契約・責務・テストを修正して該当Gateを再通過する。

例:

公式サイト実運用で`home.news_items`の仕様不足が判明した場合、Phase 4内だけでテーマ側workaroundを入れず、Phase 3のNews API仕様へ戻して修正する。

## 15. ブランチ・Issue運用

- 原則としてPhaseごと、または責務単位でIssueを分ける。
- 1 PRで複数Phaseを跨がない。
- Gate通過前の次Phase実装を混ぜない。
- PR本文冒頭に「現在位置」「今回の目的」「非対象」「Gate条件」を記載する。
- 実装途中で新しい要求を発見した場合は、現在Phaseの完成条件に必要かを判定し、不要なら別Issueへ送る。
- ユーザー向け変更はCHANGELOGとrelease note候補へ記録する。

## 16. 今回の非目標

- 一般利用者向けノーコードテーマビルダー
- ブラウザ上のHTML/CSS編集
- ドラッグ&ドロップページビルダー
- テーマ内PHP実行
- 研究室専用CMS機能
- Members / Research / Publicationsの専用DB・専用管理画面
- テーマ配布サイトの即時開発
- 自動的に第三者テーマをインストールする仕組み

## 17. 完成判定

テーマ基盤拡張v1は、以下を満たした時点で完成とする。

- Tomos Updateで新テーマ基盤を既存サイトへ安全に提供できる。
- サイト固有設定とテーマ本体が分離されている。
- 構造化News APIが汎用テーマ機能として利用できる。
- Tomos公式サイトでNewsの単一正本運用が実運用されている。
- 標準テーマを技術者が安全に派生・改修できる。
- テーマ開発仕様が文書化されている。
- 研究室向けテーマを本体への業種固有改修なしに制作できる。
- 将来のテーマ配布サイトに必要な互換性・metadataの拡張余地が確保されている。

## 18. 開発時に毎回確認する一文

> 今やっている変更は、現在のPhaseの完成条件に必要か。Tomos本体の普遍的な責務か。テーマ側・サイト固有設定・将来Issueへ分離すべきではないか。
