# Tomos Core: Post認証強化の実環境検証（PR #114）

## 位置づけ

この文書は「実環境の検証手順と合否判定基準」であり、検証済みの報告書ではない。
GitHub Actionsの実行可否に依存しない。**本番公開、mainマージ、Release発行は、すべての必須項目がPASSとなるまで禁止**する。

## 検証環境・前提

- 対象: さくらインターネット上の、Tomos Core専用の**隔離された実機検証サイト**（本番の `config.php`、記事、パスキー保存領域、APIトークン、Cookieを共有しない）
- HTTPS、WebAuthn対応ブラウザ、実サーバーのPHP / OpenSSL / mbstringを使用
- サーバー側PHPバージョンと拡張機能を確認し、結果に記録する
- iPhone SafariとmacOS Safari、可能ならChromeでも検証する
- RP ID（ホスト名）にパスキーが紐づくため、別ホストのパスキーを本番へコピーして試験しない
- 検証用パスキーは2件以上登録する。秘密鍵・合言葉・APIトークンをIssueや試験報告に貼らない
- テスト用にインストールと復旧をやり直せる状態（バックアップ含む）を確保する

## 1. ローカル事前検証

1. PR #114ブランチをローカルに取得する
2. `bash tools/check-post-security-local.sh` を実行する（PHP構文、認証・パスキー関連テスト）
3. 必要に応じ、`bash tools/prepare-distribution-dependencies.sh`、`bash tools/build-distribution.sh` を使って配布ZIPとWebAuthn runtimeを検査する
4. PHP 7.4、8.0、8.2、8.5互換性は各バージョンの実行環境で個別に確認する。検証していないバージョンはPASSにしない

**注意:** ローカル試験に成功しても実ブラウザ・実サーバー試験の代用にはならない。

## 2. 実機の必須試験

| ID | 手順 | 期待結果 |
| --- | --- | --- |
| E01 | 通常モードで合言葉ログインとパスキーログイン | 両方成功し、既存投稿・設定画面が利用できる |
| E02 | 合言葉を繰り返し誤入力（パスキー登録のauthorize APIを含む） | 規定回数で一時停止し、正しい入力でも制限を迂回できない |
| E03 | 2件のパスキーを登録・名称変更する | 登録、認証、名称表示が正しい |
| E04 | パスキーで再認証して「パスキーのみ」に変更 | 設定が保存され、既存セッションと記憶認証が失効する |
| E05 | パスキー専用モードで /post/ を未ログインで開く | パスキーボタンへ誘導され、合言葉フォームは出ない |
| E06 | /post/、/post/security/、/post/passkey/manage/、/post/passkey/register/、/update/、/post/update-finalize/ に合言葉POSTを直接送る | 合言葉による新規認証が成立しない |
| E07 | 切替前にログイン済みの別ブラウザ、30日記憶Cookieから管理画面を開く | 切替前の認証は失効しており、再認証を要求される |
| E08 | パスキー専用モードで投稿、固定ページ、テーマ、設定を使用 | WebAuthnログイン後は既存機能が動作する |
| E09 | パスキー専用モードでパスキーを追加し、最後の1件を削除しようとする | 再認証後の追加が成功し、最後の1件の削除は拒否される |
| E10 | 登録済みパスキーを失う想定で、検証用サーバー上に post-reset.enable を配置して復旧する | サーバー所有者だけが合言葉の再発行と両方式モードへの復帰を行える。完了後 post-reset.enable を必ず削除する |
| E11 | 管理用合言葉を変更 | 旧合言葉と旧認証セッションは無効、API連携用トークンは意図せず失効しない |
| E12 | パスキー追加・削除、ログイン方式変更、トークン再発行を再認証なしで試す | 特権操作は拒否され、再認証後のみ成功する |
| E13 | Tomos Writeへの原稿受け渡し、Obsidian投稿API、Bluesky連携 | 既存の独立した投稿・連携トークンと必要な画面認証が維持される |
| E14 | Tomos Updateを検証用ZIPで実行（再認証・仕上げ画面を含む） | パスキー専用モードのまま更新でき、合言葉で迂回できない |
| E15 | 別ブラウザ、サブディレクトリ、HTTPS、ログアウト、端末再起動 | パスキー認証、Cookieパス、ログアウトが正常 |
| E16 | 意図的にWebAuthn依存を検証用サイトで一時的に利用不能にする | パスキー専用モードで合言葉へ自動降格しない。復旧方法が確認できる |

## 3. 合否と記録

- E01〜E16を記録し、未実施・失敗・保留が1件でもある間はリリース不可
- 試験環境のホスト名（必要なら伏せ字可）、PHPバージョン、ブラウザ・端末、テスト日時、PR HEAD、結果、修正後の再検証を記録
- 認証成功・失敗、実際の画面遷移、ログインセッションの扱いを確認する。合言葉・セッショントークン・パスキー秘密情報は記録しない
- 検証用環境を本番と取り違えない。テストで使った post-reset.enable を残さない
- 最終承認後に限り、PRをReadyへ変更してマージ/Release可否を判定する

## 実環境で確認できない事項の扱い

Chat内のGitHubコード閲覧とローカル静的テストだけでは、Face ID/Touch IDの実動作、さくら実機でのCookie・PHPセッション・更新挙動をPASSにできない。
人間がサーバーの検証サイトへ試験物を配置し、実端末で試験する工程を必須とする。

### 配置する候補

`bash tools/build-post-security-validation.sh` で次の一組を生成する。実行はローカルのみ。公式署名鍵・ネットワーク・現行サイトの設定は使用しない。

| ファイル | 用途 |
| --- | --- |
| `tomos-pr114-validation.zip` | 隔離サイトの新規設置用。VERSION `1.1.12-pr114.1`、検証専用のUpdate公開鍵を内包 |
| `tomos-pr114-update-validation.zip` | 上記サイト専用。`1.1.12-pr114.1` → `1.1.12-pr114.2`。更新本体と仕上げを試す署名付きZIP |
| `validation-public-key.pem` | ZIPの組合せ確認用の公開鍵。秘密鍵はビルド終了時に削除 |
| `SHA256SUMS` | 上記3ファイルのハッシュ |

これらは正式バージョンでも既存サイト向けアップデートでもない。既存サイトのUpdate公開鍵を検証鍵に置き換えない。公式配布・本番上書き・オンライン更新カタログへの掲載は禁止。

1. ZIPとSHA256SUMSを照合する。別ビルドの新規設置ZIPと更新ZIPを混ぜない（検証鍵が毎回変わる）。
2. さくらに新規の隔離ディレクトリとHTTPSの検証URLを用意する。本番と設定・記事・保存領域を共有しない。Cookieの混在を避けるため専用ホストを優先する。
3. 新規設置ZIPを空のディレクトリへ展開する。`config.php` は検証サイトのsetupで新規作成する。本番からconfig.php・記事・パスキーJSON・APIトークンをコピーしない。
4. iPhone SafariとmacOS Safariで、URL・HTTPS・PHP・OpenSSL・mbstring・VERSION・候補ハッシュを記録する。機密値は記録しない。
5. 通常モードで合言葉ログインし、セキュリティ画面から検証用パスキーを2件登録する。MacとiPhoneで同一同期パスキーが共有される場合は「2台」を「2件」と数えず、管理一覧の件数を確認する。
6. E01–E16を実施する。モード切替前に別ブラウザの合言葉セッション、30日記憶Cookie、登録許可取得済みのタブを準備し、切替後に失効を確認する。再認証から301秒待つ試験も行う。
7. E06は表示確認だけで済ませない。通常モード時のフォームのaction・CSRF・Cookieを検証サイトで控え、切替後にブラウザ開発ツールまたはローカルHTTPクライアントから直接POSTする。拒否後に保護画面へアクセスし、認証成立や設定変更がないことを確認する。Cookie・CSRF・合言葉は報告に貼らない。
8. E09では別々のログイン済みブラウザから別の2件を同時削除する。最後の1件が残ること、通常モードから専用モードへの切替と削除を重ねても0件にならないことを確認する。
9. E14ではパスキー専用モードのまま `/update/` へ進み、同じ一組の更新ZIPを手動選択する。「更新内容を確認」→「更新」→Tomos Postの更新仕上げを実施し、VERSIONが `1.1.12-pr114.2` になることを確認する。途中の再認証が元画面へ戻ること、完了後も専用モード・投稿・APIトークンが保たれることを確認する。
10. E16の依存停止は検証サイト内だけで行い、テスト直後に復元する。E10の `post-reset.enable` も必ず削除する。復旧は意図的なサーバー所有者操作であり、専用モードの通常ログイン経路とは区別する。
