# v0.6.2 Browser Update Incident

Date: 2026-09-02

## 結論

今回の重大事故は単一のバグではない。

最も重大だったのは、**実環境の `v0.6.1 -> v0.6.2` Browser Update成功を確認しないまま、正式Release完了と判断したこと**である。

Cloudflareは原因ではない。

## 直接原因

### 1. Theme rulesのruntime配置と必須ファイル検証が分離していた

v0.6.2で次がruntime必須になった。

```text
docs/theme/theme-rules.json
```

しかしUpdate ZIPでは、保護対象ファイルとして一度、

```text
core/updater-pending/theme-rules.json
core/updater-pending/theme-rules.meta.json
```

へ配置し、更新後にruntimeへ反映する設計だった。

一方、旧検証処理はruntimeへの反映前に、

```text
docs/theme/theme-rules.json
```

の存在を確認した。

その結果、

1. 更新処理自体は進む。
2. Theme rulesはpending領域に存在する。
3. runtime pathにはまだ存在しない。
4. 必須ファイル検証が失敗する。
5. rollbackする。

つまり単純なZIP欠落だけではなく、**Update ZIP内の表現と、更新後runtimeの完成状態を同じものとして扱っていた**ことが根本原因だった。

### 2. 旧Updaterがcatalog全体を先に拒否した

v0.6.3では、

```text
0.6.1 -> 0.6.3
0.6.2 -> 0.6.3
```

をcatalogへ追加した。

しかし旧Updaterは、現在version向けentryを選ぶ前にcatalog全体を検証していた。

そのため旧Updaterが `0.6.1 -> 0.6.3` を処理する際、別entryの `0.6.2` を「飛越し中間version」と誤認し、catalog取得段階で停止した。

これが、

```text
オンライン更新ZIPを取得できませんでした
```

につながった別系統の障害だった。

### 3. テストが実artifact・実環境を保証していなかった

既存テストには、公開artifactや必要環境がない場合に `SKIP` して終了コード0となるものがあった。

また、package builderの検査と、実際の旧version環境からのBrowser Update検証が分離していた。

不足していたGateは次のとおり。

- 公開済みUpdate ZIPを使用した実更新
- v0.6.1実installからの更新
- 旧Updaterでのcatalog読み込み
- PHP実行方式でのZIP取得
- runtime必須ファイルの配置後検証
- 更新後の実サイト起動確認

## 緊急対応で混乱した理由

次を一つのrelease transactionとして管理できていなかった。

- Core source
- Update ZIP
- catalog
- mirror
- GitHub asset
- 公式Downloadページ
- News
- 各サイトの旧Updater

その結果、中央artifactを修正しても、既存サイトの旧Updaterが中央情報を読む前に停止する状態が残った。

同一URLのZIP差し替えも、cache、SHA、catalog、旧Updaterの状態を複雑にした。

## 根本的なRelease判断上の問題

package作成、Updater、catalog、公開artifact、実サイト更新を別々にPASS判定していたことが本質的な問題だった。

今後の正式Release完了条件は、サポート対象の旧実環境から公開artifactを使用したBrowser Updateが最後まで成功することとする。

```text
旧実環境
  -> 旧Updater
  -> 公開catalog
  -> 公開Update ZIP
  -> PHP実取得
  -> 検証
  -> 展開
  -> runtime完成
  -> 実サイト起動
  -> 保護データ保持
```

この一連を一つのAcceptance Gateとして扱う。

## 同一version緊急更新の方針

通常UpdateとRecovery Updateを完全に分離する。

Recovery Updateでは、

- `mode=recovery` の場合のみ同一versionを許可する。
- `from` は現在versionと完全一致させる。
- 署名を必須とする。
- 通常version更新とは別entryにする。
- `repair_id` を付与する。
- 同じZIP URLを上書きしない。
- 新しい修正ごとに新しいimmutable artifactを発行する。
- 成功した `repair_id` をruntimeへ記録し、再表示・再適用しない。
- Updater、Core、runtime必須データなどallowlist対象だけを更新する。

次はRecovery対象外とする。

- `config.php`
- `content/`
- uploads
- custom Theme
- サイト固有設定・運用データ

詳細は `docs/release/recovery-update.md` を正本とする。

## 旧Updaterへの対応限界

Recovery Updateを理解しない旧Updaterは、中央catalogを変更するだけでは同一version更新を開始できない。

したがって、

- Recovery対応Updater: 同一version recoveryを利用できる。
- v0.6.1 / v0.6.2等の旧Updater: まずRecovery対応versionへ通常更新する。
- それ以前または通常Updateへ到達できない環境: 対応する通常Updateまたは手動bootstrapが必要。

旧コードへ一度も到達できないサイトを、中央側だけで強制的に同一version更新へ切り替えることはできない。

## 今後のRelease必須Gate

1. 実際に生成したUpdate ZIPを使用する。
2. 全サポート対象version / Updater実装から更新する。
3. 旧Updaterでcatalogを読み込む。
4. PHP実取得方式でZIPを取得する。
5. SHA-256、署名、manifestを確認する。
6. runtime必須ファイルを配置後に確認する。
7. `config.php`、`content/`、uploads、custom Theme保持を確認する。
8. 意図的欠落ZIPでrollbackを確認する。
9. 必須Gateの `SKIP` は成功扱いにしない。
10. 公開URLからartifactを再取得して最終PASSする。
11. 更新後の実サイト起動を確認する。

## 再発防止の原則

**Release artifactが正しいことと、既存ユーザー環境からReleaseへ到達できることを分離して判断しない。**

正式Release完了は、公開artifactによる実更新成功によってのみ確定する。
