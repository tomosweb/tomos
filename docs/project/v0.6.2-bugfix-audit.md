# Tomos v0.6.2候補 Bug-fix Audit

監査基準: Core `65dec67e63ce4b530e776bebf1f154d04c48486b`、作業時の `VERSION` は `0.6.1`。この文書はv0.6.2候補の監査記録であり、v0.6.1の公開物・tag・Release・Installer・`latest.json`・productionを変更しない。

## 結論

- v0.6.2へ入れるべき修正: Theme rule runtime依存ファイルをUpdateとinstalled-file契約へ追加、全体CSP緩和フラグを削除、CSP生成をfail-closedの純粋クラスへ分離、Core側canonical rules hashとBrowser側比較toolを追加。
- Developer Center公開に必要な修正: 公式サイト側で`/themes/`の実ディレクトリ衝突を解消し、Browser bundleへCoreと一致する`RULES_HASH`を埋める。公式サイトcheckoutとproductionは今回変更していない。
- reserved slugの新規拒否、global rewrite変更、custom Theme JavaScript許可は互換性影響があるため、今回実装しない。

## 1. Reserved URL / Router

Tomos Routerは予約namespaceを知らず、通常のcontent候補を返す。たとえば`/themes/`は`content/themes/index.md`、`/themes`は`content/themes.md`または`content/themes/index.md`として解決可能で、Router単体の優先順位はmetadata index、virtual folder、PageRepositoryの順である。

Apacheの現行`.htaccess`は`!-f`かつ`!-d`のときだけ`index.php`へrewriteする。したがって実ディレクトリがRouterより先に優先される。`Options -Indexes`のため、indexのない`/themes/`、`/core/`、`/content/`はproduction Apacheでは403になり得る。PHP built-in serverで同じcheckoutを読み取り確認した結果は、`.htaccess`を読まないため、これらの実ディレクトリは404、存在しない候補はconfig未作成時のsetup 302になった。Nginxは設定ファイルがないため挙動未確認で、`try_files $uri $uri/ /index.php`なら同じく実ディレクトリ優先が想定される。

| namespace | 現在の実体 | fixed page / article slug | Router | server-side risk | 判断 |
|---|---|---|---|---|---|
| `/themes/` | `themes/` | 作成可能 | content候補へ解決 | Apache 403、local 404、sitemapにdead URLが混入し得る | Developer Center blocker。予約拒否・rewriteは別設計 |
| `/assets/` | Core rootにはなし | 作成可能 | content候補へ解決 | hosting側の実assets directoryができると同様 | 現在は変更しない |
| `/admin/` `/api/` | Core rootにはなし | 作成可能 | content候補へ解決 | 将来endpoint追加時に衝突 | 予約候補として文書化 |
| `/core/` `/content/` `/data/` | `core/`, `content/`あり | 作成可能 | content候補へ解決 | 実directory優先、source/static exposureの追加リスク | reserved候補。publish拒否は延期 |
| `/includes/` `/templates/` `/uploads/` | Core rootにはなし | 作成可能 | content候補へ解決 | hosting・custom deployment次第 | reserved候補。変更なし |
| `/post/` `/setup/` `/update/` | endpoint directoryあり | 作成可能 | content候補へ解決 | PHP endpoint/static fileが優先 | 現行互換を維持 |
| `/cache/` `/storage/` `/trash/` `/tools/` `/docs/` | runtime/source directoryあり | 作成可能 | content候補へ解決 | 直接アクセス・403/404差 | 予約候補。web server protectionを別途確認 |
| `/search/` `/tags/` `/feed.xml` `/rss.xml` `/sitemap.xml` `/robots.txt` | Core endpoint | 作成可能（一部は特別処理） | 特別routeが優先 | endpointとcontentの意味が衝突 | 現行routeを維持 |

固定ページslugと記事slugは現状publish時に予約namespaceを拒否しない。既存contentに影響するため、禁止を導入するなら既存URL inventory、migration/redirect、admin warning、publish-time hard failの順で別承認が必要であり、v0.6.2のこのbug-fix branchでは導入しない。canonical、sitemap、RSSはcontent metadataから生成されるため、予約slugを許可したままではserver実体との不一致が各出力へ残る。

## 2. CSP

`core/App.php`は全route共通でCSPを送信し、GA4ありの場合だけGTM hostとnonceを`script-src`へ追加する。GA4なしまたはnonce生成失敗時は`script-src 'none'`である。`default-src 'self'`は残るが、script sourceへ`'self'`を足す設計ではない。

`allow_theme_scripts`はv0.6.1後のDeveloper Preview追加commit `ddd268c38bc744bdbe21645c907130c01cd8e6c5`でconfig.sampleとAppへ同時に導入された。既存release由来の設計ではなく、文書化もなく、trueにするとcustom Themeを含む全same-origin scriptをglobalに許可するため、今回削除した。

Developer Centerの許可方式はCoreのcustom Theme権限と分離する。推奨は、公式サイトの管理routeだけでresponse nonceを生成し、Coreが管理する固定script elementへnonceを付け、そのrouteのCSPを`script-src 'nonce-...'`（必要ならGTMのみ追加）とする方式である。`'self'`、`unsafe-inline`、content本文のscript許可、Theme configからのCSP source注入は行わない。Coreは公式サイト固有routeをハードコードしない。

## 3. Theme rule parity

Coreの`ThemeValidator`と`ThemePackagePolicy`のrequired files・Core patternは`docs/theme/theme-rules.json`から読む一方、Browser mirrorは公式サイトの`assets/theme-validator.js`へ手動vendoringされている。現状のBrowser bundleには`RULES_HASH`がなく、Core JSONと機械的に一致確認できない。今回の採用方式は案C: Coreのcanonical JSON SHA-256を`ThemeRules::sha256()`で計算し、Browser bundleの`RULES_HASH`と`tools/check-theme-rules-parity.php`で比較する方式である。repo間の自動書き換えは行わない。

今回、公式サイトのmirrorへhashを追加していないため、parity gateの現状は未達であり、Developer Center公開Blockerとして残る。

## 5. Existing bug regression audit

- P0: v0.6.1からの自動Update差分が`docs/theme/theme-rules.json`を落とすと、更新後の`ThemeRules`依存が欠落してTheme validation/package policyがruntime errorになる。今回修正済み。
- P1: `/themes/`など実directoryとcontent routeの衝突。Apache 403、local development 404を再現。既存URL互換性を考慮したroute/rewrite方針が未承認のため、今回修正せずDeveloper Center blockerとした。
- P1: `allow_theme_scripts=true`がglobal same-origin scriptを許可。v0.6.1後の未公開Preview基盤で再現可能な設計bug。今回削除済み。
- P2: Browser mirrorがCore rules hashを持たず、rule driftをCIで検知できない。hash checkerを追加したが公式サイト側未接続。
- Deferred: Nginx正式設定、reserved namespaceのmigration、publish warning/hard failの段階導入、route-specific CSPの公式site実装、browser mirrorのCI接続。

## 6. Compatibility / Production blocker

既存releaseのCSP動作は維持し、`allow_theme_scripts`はv0.6.1 artifactに存在しないためrelease artifactへ変更はない。新しいconfigでglobal Theme scriptを許可する利用者向け契約は追加しない。Updateでは新規runtime依存を同じpackageへ含めるため、v0.6.2 update pathの互換性を改善する。

Production deploy、official-site変更、VERSION更新、tag、GitHub Release、Distribution/Update公開、Installer/latest更新は未実施。Developer Center公開は、少なくとも`/themes/`実directory衝突の解消、公式Browser mirrorの`RULES_HASH`一致、実production HTTP/DOM/CSP確認までBLOCKED。
